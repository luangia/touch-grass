# Stage 8: FastAPI Backend

> Status: **prepared, not implemented.** Code snippets show the planned approach.
> Numbers marked **(prototype 2026-11-23)** come from throwaway SQL run against the loaded dev database (run `7c1fc6efaf00effa`, commit `0b7fd58`) from the scratch area. No project code was changed.

## 1. Objective and expected outcome

A **read-only, typed HTTP API** over the PostGIS database. It's the only thing the Stage 9 map will talk to:
- Regions and their metadata.
- Analysis areas as **GeoJSON** with headline metrics.
- Full metrics for one area, side-by-side comparison, and rankings.
- Parks as GeoJSON.
- Census blocks as **vector tiles (MVT)** generated by PostGIS.
- A methodology endpoint (parameters, sources, licences, caveats) and a health check.

`uv run uvicorn touchgrass_api.main:app` serves it, with interactive docs at `/docs`. Every endpoint is tested against the test database.

## 2. Why this stage exists

The analysis lives in tables. A browser can't (and mustn't) query PostGIS directly. The API is the **contract** between data and map. It decides what's public, gives every response a validated shape, keeps payloads small enough for a phone, and refuses bad input with clear errors. It's also where the D-010 decision lands: GeoJSON for the small layers, vector tiles for the dense one.

## 3. Dependencies

- **Stage 4:** schema, GiST indexes, the `regions` row with the config as jsonb, and `datasets` (provenance, attribution).
- **Stages 6–7:** `analysis_runs` (`is_latest`), `block_access`, `metrics_runs`, `area_metrics`, `area_thresholds`, `area_context`, `block_park_reach`.
- **Decisions:** D-009 (FastAPI + Pydantic; raw SQL allowed), D-010 (GeoJSON first, MVT for blocks), D-011 / D-022 (what may be ranked: share and priority only for `ranked` areas; ACS context never ranked), D-004 (no region constants in code).

## 5. Concepts

### 5.1 REST resources
Model the API as nouns with stable URLs, and let HTTP verbs and status codes carry the meaning:

```
/api/v1/regions                               collection
/api/v1/regions/{region_id}                   one region
/api/v1/regions/{region_id}/areas?type=…      sub-collection, filtered
/api/v1/regions/{region_id}/areas/{area_id}/metrics
```
- **`/v1`** lets a later version change shapes without breaking the map.
- **404** for an unknown region or area. **422** for invalid parameters: a threshold that isn't 5/10/15, or `z` out of range (FastAPI produces these automatically from type hints).
- **Read-only:** GET only, so every response is cacheable.

### 5.2 FastAPI: path operations, dependency injection, validation
FastAPI reads your function signature and builds parsing, validation and the OpenAPI docs from it:

```python
@router.get("/regions/{region_id}/rankings", response_model=Ranking)
def rankings(
    region: Region = Depends(get_region),          # 404 if unknown; reused by every route
    metric: RankMetric = RankMetric.pct_within,    # Enum → only allowed values (422 otherwise)
    threshold: int = Query(10),                     # checked against the region's thresholds
    limit: int = Query(10, ge=1, le=100),
    conn: Connection = Depends(get_conn),           # a pooled connection, returned after
) -> Ranking: ...
```
**Dependency injection** (`Depends`) is how shared needs are written once: a DB connection, "load the region or 404", "resolve the latest run". Tests can override a dependency, for example to point it at the test database.

**Pydantic response models** are the contract. The response is validated on the way *out* too, so a SQL change that drops a field fails a test instead of breaking the map silently.

### 5.3 Sync endpoints and a connection pool
Opening a PostgreSQL connection costs a TCP + auth handshake (milliseconds). A **pool** (`psycopg_pool.ConnectionPool`) keeps a few open and lends them out per request.

FastAPI runs plain `def` endpoints in a thread pool, so blocking psycopg calls don't stall the server. `async def` + `AsyncConnectionPool` only pays off at concurrency levels a public map of one city won't reach (Q2).

### 5.4 GeoJSON (RFC 7946)
- A `FeatureCollection` of `Feature`s, each with `geometry`, `properties` and an optional `id`.
- Coordinates are **longitude, latitude in WGS 84 (EPSG:4326)**. That's exactly our storage CRS (D-008), so no transform is needed for output.
- **Precision:** 6 decimals ≈ 0.1 m, beyond what any web map shows. Full precision (15 digits) only adds bytes: 441 → 355 KiB.
- **Simplification for transport:** drop vertices that move a line by less than a tolerance. Do it in **meters**: transform to the region's analysis CRS, simplify, transform back. A degree-based tolerance means different distances at different latitudes. `ST_SimplifyPreserveTopology` won't create self-intersections. It still simplifies *each polygon on its own*, so the shared border of two neighbors can move differently on each side, leaving slivers. At 5 m that's invisible on screen; at 20 m it's 88,000 m² for four districts.

Building the JSON in SQL avoids round-tripping geometry through Python:

```sql
SELECT json_build_object('type', 'FeatureCollection', 'features', coalesce(json_agg(
         json_build_object('type', 'Feature', 'id', a.area_id,
           'geometry', ST_AsGeoJSON(ST_Transform(ST_SimplifyPreserveTopology(
                         ST_Transform(a.geom, %(crs)s), %(tol)s), 4326), 6)::json,
           'properties', json_build_object('name', a.name, 'pct_within', t.pct_within, …))
         ORDER BY a.area_id), '[]'::json))
FROM touchgrass.analysis_areas a
JOIN touchgrass.area_metrics m USING (region_id, area_id)
JOIN touchgrass.area_thresholds t USING (region_id, run_id, area_id)
WHERE a.region_id = %(region)s AND a.area_type = %(type)s
  AND m.run_id = %(run)s AND t.threshold_min = %(threshold)s;
```

### 5.5 Vector tiles (MVT)
**Intuition:** instead of sending all blocks at once, cut the world into a pyramid of square tiles and send only the tiles on screen, at a detail level that matches the zoom.

- **Tile pyramid (XYZ / "slippy map"):** at zoom z the world (Web Mercator, EPSG:3857) is a 2^z × 2^z grid. Tile (z, x, y) has x counting east from −180° and y counting south from about 85°N. Portland's center is tile 12/652/1465.
- **MVT** (Mapbox Vector Tile) is a protobuf. Each tile holds layers of features whose coordinates are **integers in a local grid** (extent 4096 × 4096). That quantization is a free simplification: at z12 one grid unit is 2.4 Mercator meters, about 1.7 m on the ground at Portland's latitude.
- **PostGIS does it in three functions:**

```sql
WITH b AS (
  SELECT ST_AsMVTGeom(ST_Transform(cb.geom, 3857),       -- to tile CRS
                      ST_TileEnvelope(%(z)s, %(x)s, %(y)s), -- the tile's bounds in 3857
                      4096, 64, true) AS geom,             -- extent, buffer, clip
         cb.geoid20, ba.pop20, ba.network_m, ba.walk_min, r.reachable_park_ha
  FROM touchgrass.census_blocks cb
  JOIN touchgrass.block_access ba USING (region_id, geoid20)
  LEFT JOIN touchgrass.block_park_reach r USING (region_id, run_id, geoid20)
  WHERE cb.region_id = %(region)s AND ba.run_id = %(run)s
    AND cb.geom && ST_Transform(ST_TileEnvelope(%(z)s, %(x)s, %(y)s), 4326)  -- index-friendly
)
SELECT ST_AsMVT(b, 'blocks', 4096, 'geom') FROM b;
```
- **The index trap:** writing `ST_Transform(cb.geom, 3857) && envelope` transforms every block before it can compare, so the GiST index on `geom` (4326) can't be used. Transform the *envelope* to 4326 instead and compare against the indexed column.
- **Buffer (64)** keeps a little geometry outside the tile so outlines don't show seams at tile edges. **Clip** cuts everything else off.
- **Zoom range:** at z10 one tile is the whole city (393 ms, 661 KiB). From z12 every tile is under 50 ms and 181 KiB. So blocks are served from **z12**, and the map shows neighborhoods (GeoJSON) below that. MapLibre **overzooms**: at z16 it reuses the z14 tile, so the server only needs z12–14 (Q6).

### 5.6 SQL injection and identifiers
**Values** always go in as parameters (`%(region)s`), never by string formatting. psycopg sends them separately from the SQL text, so `'; DROP TABLE` is just a string.

**Identifiers** (column names) *can't* be parameters. A ranking "by metric" therefore maps an `Enum` to a **fixed whitelist** of column expressions, and the user's text never reaches the SQL:

```python
class RankMetric(StrEnum):
    pct_within = "pct_within"; underserved_pop = "underserved_pop"; priority_score = "priority_score"
ORDER = {RankMetric.pct_within: "t.pct_within ASC", RankMetric.underserved_pop: "m.underserved_pop DESC", …}
```

### 5.7 Which run? The database as the contract
Tables hold several runs (history). The API answers for the **latest** run (`analysis_runs.is_latest`), resolves its id **once** per request, and passes it on as a parameter. The prototype found the inline join much slower in the tile query.

Every response carries `run_id`, so the map can show which run it's looking at and caching can key on it.

The API doesn't import the pipeline. Their shared interface is **the schema**: the API checks at startup that the database is at the migration version it was written for, and `/health` reports it.

### 5.8 Caching and compression
- **gzip** (FastAPI's `GZipMiddleware`) shrinks GeoJSON about 4×; MVT about 2×.
- **ETag = run_id:** data only changes when a new run is loaded. `Cache-Control: public, max-age=…` plus an `ETag` lets the browser revalidate cheaply. Tiles are immutable for a given run.

### 5.9 Read-only by construction
The API connects with `default_transaction_read_only = on`, so even a bug can't write. A dedicated SELECT-only role belongs with deployment (Stage 11).

### 5.10 CORS
The Vite dev server (`http://localhost:5173`) and the API (`:8000`) are different **origins**. Browsers block cross-origin reads unless the server sends `Access-Control-Allow-Origin`. `CORSMiddleware` allows a configured list of origins, GET only.

## 6. How the concepts relate

```
browser (Stage 9) ──HTTP GET──► FastAPI app
                                  │  CORS · gzip · ETag(run_id)
                                  ▼
                       path operation (validated params: Enum, ranges)
                                  │  Depends: pool → conn (read-only) → region (404) → latest run_id
                                  ▼
                       parameterized SQL ──► PostGIS
                         areas/parks: json_build_object + ST_AsGeoJSON(simplified, 6 dp)
                         blocks:      ST_TileEnvelope → ST_AsMVTGeom → ST_AsMVT (z12–14)
                         metrics:     area_metrics ⋈ area_thresholds ⋈ area_context
                                  ▼
                       Pydantic response model (validated) or raw bytes (MVT, prebuilt GeoJSON)
```

## 7. Fit in the architecture

```
api/                                  (NEW, its own uv project; does not import the pipeline)
  pyproject.toml                      fastapi, uvicorn, psycopg[binary], psycopg-pool, pydantic-settings
  src/touchgrass_api/
    main.py          app factory: routers, CORS, gzip, lifespan (pool open/close, schema check)
    settings.py      DATABASE_URL / POSTGRES_* (same resolution rules as the pipeline), CORS origins
    db.py            pool, read-only connection dependency, expected schema version
    deps.py          get_region (404), latest run, threshold validation
    models.py        Pydantic response models
    queries/         SQL strings (one module per resource)
    routers/         regions, areas, parks, tiles, methodology, health
  tests/             TestClient against touchgrass_test, seeded by the pipeline's synthetic region
```

- **Why a separate project:** the pipeline pulls in OSMnx, SciPy, GeoPandas and GDAL. The API needs none of them, and Stage 11 deploys the API alone.
- **The cost:** a small copy of the connection-settings logic, plus a **dev-only** dependency on the pipeline so tests can build and load the synthetic region (Q1).
- **The caveat text** currently lives only in the Stage 7 markdown report. To serve it from `/methodology` without copying prose, the pipeline writes the same list into the metrics run record. It's then loaded into `metrics_runs.summary`, and the API reads it from there. That's one small pipeline change in this stage (Q9).

## 8. Implementation approach

1. **Project skeleton:** `api/pyproject.toml` (same `exclude-newer` policy as D-014), app factory, settings, pool, and the schema-version check.
2. **Regions:** list (name, bbox from `study_boundaries`, default view), plus detail: thresholds, data vintages from `datasets`, latest run, area types.
3. **Areas:** GeoJSON per type, with the headline metrics for one threshold (default = the underserved threshold).
4. **Area metrics:** all thresholds, per-area values, and ACS context with MOE / CV / reliability.
5. **Compare** (≤ 10 areas) and **rankings** (whitelisted metrics; `ranked` floor for share/priority; ties broken by area_id).
6. **Parks:** GeoJSON, simplified, with class and area.
7. **Block tiles:** MVT for z12–14; 204 for empty tiles; ETag.
8. **Methodology:** run parameters, sources + attribution + licence links from `datasets`, caveats from the metrics run.
9. **Health:** process up, DB reachable, schema version.
10. **Tests, a latency check, and docs.**

### 8.2 Testing strategy
- **Test database seeded with the pipeline's synthetic region** (3 blocks, 2 parks, 2 neighborhoods, 2 districts). The same fixture the pipeline tests use, run through process → network → analyze → metrics → load.
- **Contract tests:** every endpoint is validated against its response model. GeoJSON is checked for structure (`type`, coordinates within ±180/±90, longitude first).
- **Errors:** unknown region or area → 404; a bad threshold, metric or zoom → 422; too many compare ids → 422.
- **Tiles:** a tile over the synthetic city decodes (`mapbox-vector-tile`, test-only dependency) to a `blocks` layer with the expected geoids and attributes. A tile elsewhere → 204.
- **No region constants:** the hardcoding guard extended to `api/src`.
- **Latency (acceptance):** p95 of the area list against the real Portland database < 500 ms (`-m data`; the prototype's SQL is about 25 ms).
- **Read-only:** a test proves an attempted write on the API's connection fails.

## 12. Questions to think about before we start
1. Why does `cb.geom && ST_Transform(envelope, 4326)` use the index while `ST_Transform(cb.geom, 3857) && envelope` can't?
2. The z12 tile query scanned the whole table instead of using the index. Why can that be the *right* choice, and at which zoom would you expect the index to win?
3. A ranking endpoint takes `metric` from the URL. Why can't it be a SQL parameter like `region_id`, and what stops `?metric=1;DROP TABLE` from doing harm?
4. Why simplify in meters (the analysis CRS) instead of degrees? What goes wrong with a 0.0001° tolerance between Portland and Anchorage?
